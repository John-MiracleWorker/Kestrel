# Implementation Status

Last updated: 2026-07-28

This repository is a production candidate for the supported single-user, single-node local/private profile. Hosted/team identity, multi-tenant isolation, distributed scheduling, and unsupported extension surfaces remain outside that profile. The status below is intentionally literal so future Codex passes can harden those broader surfaces without weakening the supported contract.

## Working Now

- CLI chat loop with in-memory and Memvid `.mv2` memory backends.
- GitHub curl one-shot installer for the local Memvid-backed agent runtime, with dry-run, Python 3.11-through-3.13 enforcement, macOS and Linux-x86_64 platform checks, immutable release-commit binding, web build, memory verify, deterministic `mock` smoke checks, and opt-in detached server startup, `/api/health` polling, and browser launch for the local web UI.
- Layered memory files for working, episodic, semantic, procedural, self, and policy layers.
- Context compiler that retrieves nested memory and builds the model prompt.
- MV2 context-frame model and token-aware pseudo-context packer that retrieves summaries first, deduplicates content, flags conflict metadata, and expands raw evidence on demand.
- Exact recent-session transcript reconstruction from durable working-memory user/assistant frames, bounded to the 8 most recent completed turns and 8,000 characters, with explicit role ordering, durable origin/scope labels, exclusion of the live turn, and exclusion of scheduler, subagent, and approval-continuation turns from native user transcript replay.
- Persistent recall trust boundary: packed memory and failure lessons are JSON-encoded as untrusted user-role evidence, so content copied from tools, web pages, files, or channels is never injected as a system-priority instruction. Soul system content is limited to the fixed persona preset selected through the authenticated onboarding route; display labels and free-form Soul preferences are bounded untrusted JSON at user-role priority. Policy recall receives system priority only when `memory.policy_promote` metadata cross-checks against the durable owner-approved exact call and its recorded result. Activated behavior deltas remain separate trusted runtime messages, and deterministic capability/approval gates remain authoritative.
- Soul/self memory layer backed by `.nest/memory/self.mv2`, packed after policy and before procedural memory, with `self_model` context frames and conservative promotion gates.
- Deterministic mock provider for fast tests and reproducible golden evals.
- OpenAI Responses provider adapter using the portable JSON tool envelope.
- OpenAI Responses provider now exposes native streaming deltas when the SDK stream surface is available, while preserving the non-streaming fallback path.
- OpenAI-compatible chat completions provider for local/model-server endpoints, with native Chat Completions tool-call normalization and streaming text/tool-call assembly.
- OpenRouter and Ollama provider aliases route through the OpenAI-compatible contract with provider-specific defaults.
- Anthropic Messages and Gemini provider adapters now implement the same strict Kestrel response contract with native tool-use/function-call normalization and SDK-stream surface support.
- Codex CLI provider that can use local `codex exec` as the normal response engine.
- Provider capability metadata is exposed on built-in providers, including an optional native-tool budget for constrained local models, and a retryable-error fallback wrapper can route from a primary provider to a configured secondary provider. Native schemas are supplied only through provider tool interfaces; bounded catalogs are relevance-ranked from the live capability-filtered registry and keep `tool.registry` available for discovery.
- Bounded provider discovery can read Ollama, LM Studio, and generic OpenAI-compatible model catalogs, probe generation/streaming/tools/structured-output behavior, retain evidence provenance and freshness, and create disabled target drafts. Removed discovery-managed models become stale; Local Only, Balanced, Cheapest Validated, Fastest, Frontier Review, and Privacy First presets constrain existing eligibility rather than granting it.
- Built-in tool registry with structured exception boundaries, timeout enforcement, tool/source/risk introspection, and exact-call approval gates for shell, file writes, patch application, tests, and Codex CLI delegation.
- Self-diagnosis primitives can classify common provider/tool/test/import/permission/MCP/sandbox failures and recall similar procedural/episodic failure lessons before retry.
- The default-on agentic failure cycle retrieves prior failure lessons before tool planning, records failed tool attempts as episodic `FailureEpisode` records, blocks unchanged same-action retries until a meaningful changed strategy is supplied, and returns a structured proof-of-work summary on agent turns. It can be disabled with `NEST_AGENT_DISABLE_AGENTIC_CYCLE=1`.
- Safe self-repair now has branch-isolated repair primitives: `repair.prepare`, `repair.status`, `repair.apply_patch`, `repair.validate`, `repair.orchestrate_validate`, and `repair.rollback`.
- Self-awareness tools now expose non-secret identity, runtime config, provider capability, memory layer, tool, skill, plugin, MCP, and state snapshots through `self.inspect`, `self.reflect`, `self.remember`, and approval-gated `self.propose_change`.
- Gated web context tools now provide read-only `web.search` and `web.fetch`, disabled by default behind `NEST_AGENT_ALLOW_WEB`, with deterministic mock backend support, citations, byte/time/result limits, redaction boundaries, and private/local network URL rejection.
- The first diagnosis-gated repair orchestration slice can run validation on an active repair branch, classify failures, recall prior lessons, and block repeated validation retries until the strategy changes.
- Skills now have a first manifest validation gate plus persisted validation/provenance metadata for discovered instruction capsules, and discovery returns structured counts, empty-directory messages, and validation errors.
- Local FastAPI control plane with background runs, SSE events, approvals, tools, a server-authoritative capability catalog/mutation/history API, MCP registry, skills registry/discovery reports, Secret Broker metadata routes, memory search, Soul/self routes, gated web routes, non-secret runtime config, channel CRUD, plugin/skill detail, memory inspect, cognition lesson/failure lists, and diagnosis classify/recall routes.
- Local operator web UI now opens on task-first Mission Control: project selection, objective templates, repository/provider/budget/permission preflight, an acceptance-oriented editable plan, run timeline, and coherent repair review. The existing provider, routing, memory, MCP, plugin, skill, channel, observability, routine, and administration surfaces remain available behind progressive disclosure.
- Mission preflight and launch are bound to the exact project revision, objective, plan, routing inventory/policy, Git branch/HEAD/tree/worktree state, and repository-index baseline. Editing a plan requires a fresh server preflight; drift fails launch instead of silently changing authority.
- The repair review panel consumes only bounded current-schema projections, maps acceptance criteria to recorded validation evidence, renders redacted unified/split diff previews, and shows review summary, risk, and rollback state. Local commit and exact patch export remain high-risk exact-call actions.
- Mission Control's engineering run panel keeps per-call approval packets, graph amendments, candidate comparisons, browser evidence, and review-bound GitHub change requests in the same durable run view. Packet approval never collapses the individual exact-call identities, arguments, capability revisions, or resource digests, and packet display fields reject registered secrets before persistence.
- Bounded graph amendments can add, split, cancel, or replace task dependencies; they reject cycles, excess nodes, unpermitted tools, stale graph digests, non-finite JSON, registered secrets, and silent risk/cost/scope expansion. Recovery can add one evidence-driven diagnostic/retry pair and remains replayable through the amendment ledger.
- Candidate fan-out can materialize two-to-eight same-contract task attempts in distinct planned worktrees, retain rejected evidence, and select only from authenticated repair validation/review receipts using deterministic risk/diff/cost/latency ranking. Candidate results and review provenance reject registered secrets before durable persistence; model preference alone cannot select or merge a candidate.
- `browser.validate` binds a digest-pinned OCI invocation to the exact repair candidate, runs the project server and browser together with no live network, accepts only exact fixture-backed non-local requests, rejects registered secrets before container execution, and persists screenshot digest, DOM/console/network/accessibility evidence for review. The report must return one schema-valid, identity-matched boolean result for every requested assertion and interaction; omitted or substituted checks fail closed. It is separately default-off behind `allow_browser_validation`, remains exact-call approved through the owner-authenticated API, and has no host-browser fallback. The repository includes a version-aligned, immutable-base Playwright/axe image fixture and a networkless CI self-test.
- The Outcomes dashboard reports validated completion, time, attributable cost, interventions, approvals, candidate/browser evidence coverage, grouped route performance, and explicit missing-versus-zero metrics. Browser evidence coverage is distinct from pass rate, and the strongest-model baseline uses declared target quality rather than hindsight success. Private project benchmark cases have redacted fixtures, immutable acceptance criteria, replay records, and a redacted export path.
- GitHub change requests are prepared only from a current successful validation/review chain and reviewed commit tree. `github.pr.create` requires remote-mutation and push enablement plus exact-call approval; CI/check/review feedback is read back durably, and failed CI or requested changes can create a bounded recovery amendment without mutating the reviewed request.
- Multi-channel ingress for Telegram Bot API updates, Discord message/interaction-shaped payloads, and generic/custom webhooks, with CLI and API routes. Telegram also has webhook setup/status helpers, single-owner admin gating, natural-language admin reads, and inline-confirmed settings writes.
- SQLite state store for runs, run steps, approvals, MCP servers, skills, plugins, task nodes, subagent runs, trace spans, promotion ledger outcomes, behavior-delta ledger records, per-tool/MCP/skill capability overrides, append-only capability changes, revisioned routines, routine deliveries, and local project profiles, now initialized through schema version `21`; run rows may bind a project ID while preserving serialized turn source, origin, transcript scope, renewable approval claims, and exact scheduler task/subagent continuation bindings. Engineering ledgers use an independently versioned additive schema so their evidence records never become canonical `.mv2` memory.
- Local project profiles persist a canonical repository, default branch, allowed paths, narrowing capability ceiling, privacy class, budget, provider policy, test/build recipes, baseline index digest, optimistic revision, and redacted import/export. They are project organization for the supported single-owner runtime, not hosted tenant isolation.
- Each project can maintain a rebuildable, digest-keyed SQLite repository index separate from canonical Memvid memory. Bounded Python/TypeScript/JavaScript/Go/Rust/Java/Kotlin/Swift/text adapters record files, symbols, imports, lexical references, and test relationships; authenticated generation receipts, freshness fingerprints, and content digests fail closed on stale, incomplete, rolled-back, or tampered evidence.
- Read-only `repo.symbols`, `repo.references`, `repo.dependencies`, `repo.tests_for`, `repo.impact`, and `repo.context_pack` tools return bounded path/line/digest/freshness evidence and obey the project allowed-path ceiling.
- Capability mutations use revision compare-and-swap and return HTTP 409 on stale writes. New discovered skills and dynamic MCP/skill tools default off; API-created MCP servers are forced off until a later revisioned capability decision. Disabling denies future invocation attempts from stale registries, revokes affected pending approvals, and closes a disabled MCP server's managed session.
- Paper-guided nested learning kernel with context-flow metadata, optimizer traces, conservative continuum-memory routing, and a `memory.learn` tool/API path.
- Closed-loop learning instrumentation now records promotion decisions, later outcomes, false-positive rates, never-retrieved compaction, and deterministic operator recommendations through `nest-agent memory ledger`.
- Memory learning decisions now use structured `ValidationEvidence`, expose computed validation scores and observed evidence refs, read active `LayerSpec` validation/repeat thresholds, and mark legacy raw-score inputs as deprecated metadata.
- Backend-neutral memory mutation now supports `upsert`, `tombstone`, `iter_records`, `get_record`, inactive-record filtering, correction frames, conflict-set frames, and audit retrieval with `include_inactive`.
- Lesson cards deduplicate similar same-category procedures, merge validation evidence refs, and update cumulative success/failure repeat counts instead of creating repeated procedural duplicates.
- Retention compaction can summarize and tombstone TTL-eligible working/episodic records through `memory.compact` / `nest-agent memory compact`; it is dry-run by default and skips stable layers by default.
- Hybrid/vector retrieval is config-gated through layer specs and uses rebuildable SQLite vector sidecars keyed to `.mv2` record IDs/content hashes; policy memory remains lexical.
- Run-scoped `complete.mv2` task capsules, preview-only capsule summaries, dry-run consolidation decisions, and approval-gated capsule apply.
- MCP server records now track health metadata, tool counts, capabilities, last sync/seen/call/error timestamps, session state, failure counts, and latency.
- MCP server records now persist vetting metadata: transport/network exposure, secret-env requirements, per-tool risk/approval classification, risk reasons, and recommended trust posture.
- MCP stdio servers now have a managed lazy session lifecycle with connect/disconnect/restart/health API routes, bounded operation timeouts, config-change teardown, strict shell/proxy/eval-launch rejection, and explicit command-hash-bound approval before every manually or plugin-configured process first starts.
- First task-graph and subagent run records exist, with durable task metadata, deterministic starter plan decomposition, default-off bounded provider-refined semantic guidance for existing task IDs, in-process planner/worker/reviewer profiles, and UI/API surfaces. Provider guidance cannot rewrite task dependencies, tools, risk, or approvals; `NEST_AGENT_ENABLE_SEMANTIC_ORCHESTRATION=1` is separate from the existing agentic failure-cycle flag because it adds planner/reviewer model calls.
- Background runs now execute through a durable graph wrapper above the chat loop: `PlannerNode`, `ExecutorNode`, `ReviewerNode`, `RecoveryNode`, `MemoryPromotionNode`, and `FinalizerNode`. The wrapper persists an explicit semantic-plan source, pauses for approval waits, records recovery diagnosis, and keeps the existing chat/tool loop as the executor. Completion and approval continuation both pass through an evidence-backed reviewer artifact; JSON-capable real providers can judge bounded evidence, while mock/invalid-provider paths are labeled deterministic fallbacks.
- Terminal runs reconcile the root task to completed/failed/blocked. Non-scheduler child skeleton tasks that were never executed become `skipped`, and scheduler child-status aggregation merges into the root result without deleting its orchestration review artifact.
- Task nodes can now persist latest failure diagnosis and retry strategy metadata; failed subagents classify the failure, record a retry gate that requires changed strategy, and emit a diagnosis event tied back to the task.
- The task graph now exposes deterministic `ready_tasks` for scheduler/resume work: only approved queued/approved tasks with completed dependencies are eligible, and failed retry tasks remain blocked until their retry strategy explicitly allows a changed strategy.
- An opt-in autonomous scheduler can execute approved ready task nodes through the normal agent loop, drain bounded dependency cycles until idle, publish task/subagent events, and preserve approval blocking for high-risk tool calls.
- An independent opt-in proactive-routine scheduler persists disabled-by-default UTC one-shot, fixed-interval, and five-field cron definitions in named IANA timezones. UTC scanning handles DST gaps and repeated local instants deterministically; revision-checked owner mutations, leased and generation-fenced occurrences, deterministic internal run identities/provenance, overlap suppression, bounded polling, CLI/API/workbench controls, durable history, and manual run-now idempotency remain intact. Optional channel delivery has a destination-bound idempotency key, delivery lease/receipt history, and explicit reconciliation; ambiguous outcomes become `uncertain` and are never silently retried. Provider receipts are redacted and all persisted delivery receipts are bounded, finite, and secret-safe. Raw registered secrets are rejected from definitions, and routine enablement never bypasses exact-call tool approval.
- Scheduler and subagent task execution can opt into git worktree isolation, creating durable worker branches under a configured worktree root and recording isolation metadata on task results. Repair/code-modification scheduler tasks now default to git worktree isolation when the workspace supports worktrees, even if general worker isolation is disabled, and repair DAG tasks reuse one coherent git worktree for the run.
- Provider failures emit structured `diagnosis.classified` events so traces can explain the failure category and suggested playbook.
- Run traces now include durable span records for run, plan, `llm.request`, `tool.call`, `memory.write`, `approval.wait`, review, and eval-style recovery work.
- Repair mutation tools are high-risk, approval-gated, covered by exact-call approvals, disabled unless the matching capability is enabled, and refuse non-repair branches for patch/validate/rollback operations.
- Diagnosis-gated repair validation must remain approval-gated, refuse non-repair branches, recall similar lessons on failure, and block repeated validation retries when prior lessons exist unless a changed strategy is supplied.
- Repair commits on repair branches now require a durable `repair.review` artifact tied to a successful validation result and the current diff hash; `git.commit` refuses repair-branch commits when the review is missing, stale, or for a different branch.
- Local self-improvement is separated from remote publishing: `git.create_local_branch` and `git.export_patch` provide approval-gated local primitives, `git.commit` refuses protected branches, remote git/GitHub mutation flags default off, and `shell.run` blocks common publishing escape routes before subprocess execution. Patch export requires the current signed review ID and candidate digest, revalidates under the repair lock, and renders the exact reviewed staged/unstaged/deleted/untracked/binary tree into a bounded local artifact.
- Background repair/commit goals now seed a repair-specific task DAG that orders inspect → isolation → patch → validation → `repair.review` → `git.commit`, so the durable plan itself encodes the reviewer gate before commit.
- A repair E2E smoke test now proves a seeded failure can flow through isolated repair branch preparation, approved patching, targeted validation, `repair.review` gate creation, and blocked unapproved commit; successful validation points to `create_repair_review_before_commit` instead of implying direct commit.
- Exact-call approved repair commits derive a literal Git tree from the signed reviewed manifest in a private temporary index, bypass repository clean filters/hooks/signing, atomically compare-and-swap the branch, leave the caller index untouched on failure, and return the resulting `commit_sha` for traceability. Ordinary non-repair commits require an approved staged-tree SHA as well.
- Repair validation is OCI-only with no host fallback: a preloaded digest-pinned image receives a bounded private read-only candidate snapshot with no `.git`, `.nest`, live workspace, network, host home, or secrets. Schema-v2 validation receipts bind the isolation attestation and rotate the v2 signing key after untrusted execution; schema-v1 validation/review receipts cannot authorize review or commit. Stale repair reviews block commit. Approval-gated rollback additionally binds the exact current diff digest, journals before mutation, restores raw HEAD blobs without smudge filters, and moves overwritten/untracked files into an owner-only recovery quarantine before writing the final artifact.
- Terminal run records and approval decisions are replay-safe: late duplicate terminal transitions cannot overwrite original run results, and already-decided approval records cannot be flipped by replayed decisions.
- Approval resume flow now claims the exact approved side effect under the active run lease, renews the claim during execution, and permits only that claimant to persist the result without reopening or flipping the decision. Scheduler/public-subagent continuations bind the exact task/subagent pair until an atomic blocked or terminal transition; restart recovery suppresses replay for dead/expired claims and stale result-bound continuations. Full-flow and adversarial race tests cover approval blocking, cross-manager resume, lease/generation takeover, worker heartbeat races, cancellation, corrupt bindings, and schema migration.
- Instruction skills remain host-readable only. Executable Python/shell host runtimes fail closed; opt-in executable skills must use a digest-pinned OCI image and pass canonical default-deny scope validation, private verified skill/read-scope snapshotting, exact approval, network-none/read-only/nonroot/capability/resource limits, bounded input/output, verified timeout cleanup, and no-host-fallback execution. Live workspace binds and extension write scopes are rejected. Real Docker coverage is a required CI/release gate.
- `skill.install` provides an approval-gated local upload/install path for new skill capsules under the configured skills directory, with manifest validation and content hashes.
- The plugin registry supports public GitHub source parsing/fetching, Kestrel and limited Hermes manifests, review/install/inspect/enable/disable/update/remove commands, approval-gated `plugin.review` and `plugin.install`, and materialized skill/MCP entries. Kestrel manifests can bind normalized dependency locks, compatibility ranges, and Ed25519 signatures; source-pinned GitHub trees provide fallback provenance for unsigned manifests, while raw registered secrets are rejected. Review exposes authority deltas and separately reports source/runtime reproducibility, install persists a digest-bound receipt, unmanaged dependencies cannot claim runtime reproducibility, and an enabled update that adds authority is blocked until disable-and-review.

- Generic/custom channel endpoints can require HMAC-SHA256 webhook signatures using a per-channel secret environment variable.
- Agent-invoked `test.run`, `lint.run`, repair validation, and read-only `codex.exec` always require the configured preloaded digest-pinned OCI image; `python`/`python3` normalize to the container interpreter and no host fallback exists. The image receives a private read-only candidate snapshot with no network, credentials, or host state. Consequently, `codex.exec` is limited to an image-provided binary and offline operation. The separate `codex-cli` response provider and local MCP stdio remain host-process surfaces and fail closed when same-account-readable secret or repair trust domains exist. The owning runtime additionally serializes stdio launch against secret/repair-key publication, quiesces registered sessions first, and aborts publication if teardown cannot be verified.
- Tool-aware behavior-delta preflight now runs immediately before agent-loop tool execution when `NEST_AGENT_ENABLE_BEHAVIOR_DELTAS=1`. It compiles bounded advisory instructions from relevant active deltas, passes them through the tool context/tool-loop message, and logs activations without changing capability or exact-call approval gates.
- Explicit `/search <query>` and `/memory search <query>` commands route deterministically to `memory.search`, reducing live-provider tool-choice variance for operator/eval search tasks.
- `scripts/run_live_learning_eval.py` provides an isolated live-provider learning/safety E2E harness covering provider smoke, durable memory reopen, correction frames, NestedLearningKernel gates, task-capsule extraction, approval blocking, and behavior-delta activation logging.
- `scripts/eval_learning_architecture.py` provides the integrated learning-architecture eval harness for setup, provider smoke, agent turn, `complete.mv2` capsule, behavior-delta proposal extraction, MutationGate decisions, replay comparison, behavior compilation, tool-aware preflight activation, outcome ledger recording, and rollback verification. Mock runs are deterministic; live OpenAI/OpenAI-compatible runs are skipped by default behind `RUN_LIVE_LEARNING_EVALS=1`, call/cost/time guards, and report redaction.

The guided web setup wizard loads that report and surfaces pass/warn/fail counts plus the highest-priority checks before saving onboarding to Soul memory.

## Partially Implemented

- Streaming/provider parity: OpenAI Responses, OpenAI-compatible, Anthropic, and Gemini streaming surfaces are implemented where the SDK exposes them. Provider aliases and native adapters have deterministic contract coverage, and the flag-gated live harness now names every real provider row. Evidence strength still differs by provider, model, profile, and subject; consult the v2 matrix instead of inferring equal assurance from adapter availability. Broader credentialed CI/release coverage and richer per-provider context/JSON-mode details still need hardening.
- Repository intelligence is phase 1: structural/lexical indexing, freshness, test ownership, impact, and intent-aware context packs are implemented. A deterministic seven-language navigation gate currently requires recall@5 of at least `0.70`, current digest-bound evidence for every case, and identical replay. Language-specific semantic precision, optional embeddings, changed-file test selection in every planner/reviewer path, and a larger representative real-repository benchmark remain future work.
- Project profiles bind Mission runs, repository access, budgets, recipes, and routing policy. Project-tagged working, episodic, semantic, and procedural Memvid records are filtered at the shared retrieval boundary (including child expansion and direct tool lookup); self/policy memory stays global. Adaptive Flock decisions, verified examples, and decayed target calibration are scoped by project, task family, risk, and required capabilities.
- MCP: stdio live sessions are hardened and covered by a flag-gated integration test. SSE and streamable HTTP use the same manager path but still need real transport fixtures and production soak testing.
- Skills: filesystem discovery, manifest validation, provenance metadata, upload/install, instruction capsules, and digest-pinned OCI execution with bounded private read snapshots exist. Host Python/shell execution and executable-skill workspace writes are blocked. Quota-bounded staged writeback, package dependency management, portable non-Docker engines, richer outbound-network grants, and production soak coverage remain incomplete.
- Plugins: registry, public GitHub fetch, signed/source-pinned manifest provenance, dependency-lock and compatibility review, reproducible receipts, authority-delta-gated updates, exact-call approval, review-first web UX, skill/MCP materialization, and contained digest-pinned OCI execution for executable skills exist. Locks are reviewed and bound, not automatically installed on the host. Portable container engines, richer explicit network grants, executable Hermes-hook compatibility, curated registry distribution, and broader shared-runtime security review still need hardening.
- Codex CLI: the host `codex-cli` response provider can drive responses while same-account trust domains are absent. The distinct high-risk `codex.exec` tool is approval-gated, read-only, and OCI-only; because its container is credential-free and networkless, it is currently useful only with an image-provided offline Codex path. It is not yet a branch-isolated autonomous repair loop.
- Consolidation: capsule extraction and Nested Learning decisions exist, but auto-consolidation remains disabled by default and validation loops are still basic.
- Controlled self-modification: behavior-delta schema, SQLite ledger persistence, proposal-only task capsule extraction, repeated failed tool-call heuristic extraction, `nest-agent memory deltas propose --dry-run`, rule-based mutation-gate decisions, default-off low-risk auto-activation, a default-off behavior compiler, runtime context integration behind `NEST_AGENT_ENABLE_BEHAVIOR_DELTAS`, tool-aware preflight for active relevant deltas before tool execution, deterministic compiler replay, full mock-agent replay, integrated learning-architecture evals, live learning E2E coverage, `nest-agent memory deltas ledger` JSON reporting with advisory recommendations, preview-only skill-candidate rendering, ORACLE shadow-only behavior-delta counterfactual reporting, FastAPI behavior-delta review routes, approval-gated activate/reject/rollback review endpoints, a deterministic review/action E2E test, and an Advanced web Behavior Deltas Review panel exist for visible operator review. Approval-gated skill install from candidates and broader live-provider replay matrices remain future phases.
- Self-diagnosis: first-pass classification, memory recall tools, and the default chat-loop retry gate exist. Hybrid LLM diagnosis, reviewer-confirmed diagnosis, and cross-run retry-state matching are still next steps.
- Self-modification: the runtime can inspect itself, record validated Soul/self memories, and capture approval-gated self-change requests. Actual code changes still have to flow through existing repair and commit gates; policy writes still require explicit policy gates.
- Safe repair: branch preparation, patch application, targeted validation, diagnosis-gated retry assessment, process-signed reviewer artifacts, exact reviewed patch export, literal-tree commits, approval-before-commit orchestration, approval-bound rollback, isolated candidate registration/selection, browser evidence, GitHub PR publication, and CI-feedback recovery exist. Autonomous patch synthesis and general-purpose merging of arbitrary worker branches remain incomplete.
- Subagents: local subagent runs can be queued, tracked, and executed by scheduler runs until idle. The graph runtime can assign work to task/subagent records, scheduler/subagent execution can opt into git worktree isolation, and bounded amendments/fan-out can materialize new same-contract tasks. The provider planner does not receive unrestricted DAG authority; model-proposed amendments must still enter the deterministic amendment contract, and fully autonomous Codex-backed candidate generation remains future work.
- Channels: inbound normalization, dry-run reply payloads, generic HMAC webhook verification, Telegram secret-token verification, Telegram webhook setup helpers, and single-owner Telegram admin confirmation are implemented. Discord Gateway reads, durable channel/workspace permissions, attachments, and channel-specific rate-limit handling still need hardening.
- Proactive routines: durable scheduling/run admission, owner workbench, manual idempotent run-now, named-timezone cron/DST rules, explicit channel destination policy, delivery receipts, and uncertain-outcome reconciliation are implemented. Rich calendar recurrence, attachments, connector-specific rate-limit behavior, and proof of exactly-once behavior in arbitrary third-party systems remain outside the contract.

## Not Done Yet

- Fresh, authenticated release-CI evidence across the full provider matrix. The reporting and fail-closed checking path exists, but a provider must remain below `release_certified` whenever an exact-subject/model/profile receipt is missing, stale, untrusted, unauthenticated, skipped, or incomplete.
- Fully autonomous provider-authored plan rewriting remains unfinished. The durable amendment contract can alter the graph and the fan-out contract can materialize isolated same-contract tasks, but an LLM cannot bypass deterministic cycle, node, tool, risk, cost, acceptance, evidence, and approval gates; general Codex-backed branch merge orchestration remains unfinished.
- Adaptive Flock now captures redacted provider-attempt usage/fallback receipts, decision-snapshotted token prices, actual cost when attributable, durable static/learned/actual comparisons, per-project/family/risk/capability calibration, savings/regret estimates, and transport/capability/contract escalation semantics. Low/medium-risk learned authority is implemented but defaults closed behind explicit support, confidence, utility, cost-coverage, hard-eligibility, and replay-verification gates; high-risk routing remains deterministic.
- The governed browser-validation runtime contract, image source, CI self-test lane, and evidence UI are implemented, but an operator must still publish or acquire the qualified image, configure its immutable repository digest, and preload it on the target host; there is intentionally no host fallback or mutable-tag acceptance.
- Approval packets and outcome/private-benchmark dashboards are implemented for the local owner profile. Hosted actor identity, organization-level analytics, and statistically powered benchmark claims are not.
- Review-bound GitHub pull-request creation and CI/review-comment re-entry are implemented through the local `gh` CLI. GitHub App identity, hosted webhook ingestion, and multi-user review policy are not.
- Production authorization and user/session isolation for the UI/API beyond the local shared-token gate.
- Bot-platform-native signature/identity verification and secret rotation workflows for external channel endpoints.
- Robust MCP SSE/streamable HTTP transport fixtures and failure-recovery soak testing.
- Quota-bounded staged extension writeback with reviewed host-side commit semantics.
- Managed package/dependency installation and portable container-engine support beyond the current digest-pinned Docker/OCI runner.
- Autonomous self-improvement beyond self-change proposal capture, repair diff review, test gates, rollback, and explicit human approval.
- Hosted multi-user UI behavior, production authorization, and role-scoped operator permissions.
- Arbitrary third-party systems are not claimed to provide exactly-once effects. Kestrel binds each routine delivery to a durable idempotency key and receipt, suppresses automatic retry after an ambiguous outcome, and requires explicit reconciliation.

## Current Contract

- Recent transcript replay is limited to 8 completed real primary/channel user turns and 8,000 characters. The current user frame is excluded from both transcript replay and recalled-memory hits; internal scheduler, subagent, and approval-continuation turns carry `transcript_scope=internal` and never replay as native user authority.
- Recalled working, episodic, tool, web, file, and channel content is untrusted evidence at user-message priority, even after it persists across turns. It cannot become a system instruction through memory retrieval.
- Free-form Soul fields (`working_style`, goals, interests, and communication notes) stay in bounded, explicitly untrusted user-role JSON. Caller-asserted `self.remember` validation/source strings cannot authenticate onboarding or enter the system role.
- `memory.learn` and `memory.consolidate` cannot promote policy. The dedicated `memory.policy_promote` tool uses two separately approved phases: stage an exact episodic proposal, then promote only current-run receipts bound to that proposal and emitted by the correct validation tool class. It requires structured human-explicit validation and at least five distinct task receipt refs; raw signed artifact replay and cross-bucket substitution fail closed. System-priority recall additionally verifies the durable final approval row, exact argument digest, recorded result ID, proposal, receipts, and any signed repair/review backing.
- `memory.import` strips runtime transcript-authority fields and stamps imported records as untrusted. Approval authorizes the data write; it does not authenticate imported content as a native user/assistant transcript or validated policy.
- Transcript replay requires the current turn's exact primary/channel scope and origin. Existing lossless channel session IDs remain stable; collision-prone normalized or truncated identifiers receive a versioned digest.
- Onboarding and policy candidates are scanned and authenticated before bounded selection, so untrusted records cannot crowd a trusted persona or durable policy constraint out of system context.
- A criterion claiming tests, lint, checks, or validation passed requires trusted validation-producing evidence. Generic successful tools remain useful task evidence but cannot prove a validation outcome.
- High-risk tools require both capability enablement (matching allow flag, where applicable) and explicit approval for the exact tool-call ID and arguments before execution.
- Project capability ceilings and allowed paths can only narrow global owner authority. Mission launch revalidates the bound project revision and repository state before creating a run.
- Repository indexes are rebuildable SQLite evidence caches, never canonical `.mv2` memory. Incomplete or stale coverage cannot authorize an empty result or authoritative context pack.
- `git.export_patch` cannot export an arbitrary live diff: it requires a current schema-v2 validation/review chain and exact candidate digest, renders the signed manifest in a private Git index, refuses registered credential material, and writes only under an allowed `.kestrel/improvements` path.
- Capability switches express owner-desired state; effective state is the conjunction of that switch, immutable master/config prerequisites, launch allowlists, effective parent/plugin state, and unchanged resource digests. Enabling never bypasses an exact-call approval or master flag.
- Capability changes apply to future invocation attempts. Turning off is rechecked by stale registries and active runs before later dispatch, but it does not promise to cancel an arbitrary built-in process that already started. Turning on does not rewrite an active run's snapshotted configuration.
- Pending approvals for a disabled tool or child of a disabled skill/MCP server are denied. Approved continuations are valid only while the exact-call identity, capability revision, tool policy/specification digest, and parent resource digest still match.
- An approval packet is only a review grouping. Every displayed call keeps its own digest, single-use exact-call authorization, revision/resource bindings, and individual decision; changing any call requires a new packet/approval.
- Graph amendments and candidate fan-out cannot add undeclared authority. Amendments that expand risk, cost, permission, or scope require a decision bound to the displayed base-graph digest, and candidates must use distinct mutable workspaces.
- GitHub publication remains remote mutation: preparing the request is read-only, while publishing requires the current reviewed tree, unchanged request digest, explicit capability enablement, and exact-call approval.
- Browser validation requires both `NEST_AGENT_ALLOW_BROWSER_VALIDATION=true` and exact-call approval. The API endpoint creates the same approval-bound `browser.validate` invocation; it cannot call the container service directly.
- `NEST_AGENT_ALLOW_WEB` / `--allow-web` enables read-only web tools; web fetches reject private, local, link-local, multicast, reserved, and unspecified addresses.
- `NEST_AGENT_ALLOW_SELF_MODIFICATION` / `--allow-self-modification` only enables the high-risk `self.propose_change` request path. It does not bypass exact-call approval or the repair/commit gates.
- The agentic failure cycle is default-on through `enable_agentic_cycle`; disable it only for debugging with `NEST_AGENT_DISABLE_AGENTIC_CYCLE=1`.
- Autonomous scheduling is opt-in and bounded by `max_scheduler_tasks` / `NEST_AGENT_MAX_SCHEDULER_TASKS` per cycle and `max_scheduler_cycles` / `NEST_AGENT_MAX_SCHEDULER_CYCLES` per drain run.
- Proactive routine polling is separately opt-in through `enable_proactive_routines` / `NEST_AGENT_ENABLE_PROACTIVE_ROUTINES`; owner mutations through the API require the shared API-auth gate even on loopback. New routines start disabled, fixed intervals are at least 60 seconds, cron schedules require an explicit named timezone, and each tick is bounded by `max_routines_per_tick` / `NEST_AGENT_MAX_ROUTINES_PER_TICK`.
- Scheduled routine prompts and responses use `turn_origin=scheduled_routine` and `transcript_scope=internal`, so they do not replay later as native primary/channel user authority. A running or approval-blocked occurrence counts as active for overlap suppression.
- A routine-delivery idempotency key is bound to one occurrence, run, channel, and conversation destination. `uncertain` delivery is a reconciliation state, not permission to retry; an operator must mark it delivered/failed or explicitly request a retry.
- Automatic memory compaction is opt-in through `NEST_AGENT_ENABLE_AUTO_COMPACT=1` and dry-run unless `NEST_AGENT_AUTO_COMPACT_APPLY=1`.
- Git worktree isolation for scheduler/subagent execution is opt-in through `enable_worker_isolation` / `NEST_AGENT_ENABLE_WORKER_ISOLATION`; isolated worker branches use `worker_branch_prefix` and `worker_worktree_dir`.
- Cancelled runs must not transition to completed, blocked, or failed after cancellation; lifecycle updates should use the guarded state transition helper.
- Completed, failed, and cancelled runs are immutable even for repeated same-status transition attempts; approval requests are immutable after leaving `pending`.
- Tool execution is bounded by `tool_timeout_seconds` / `NEST_AGENT_TOOL_TIMEOUT_SECONDS`, including bounded cancellation and settlement windows. Cooperative subprocess tools return a structured timeout only after verified process-tree cleanup. If arbitrary tool code or its cancellation hook cannot be proven settled, Kestrel returns nonretryable `tool_outcome_unresolved`, requires reconciliation, retains run-owned resources until late threads settle, and quarantines that tool across registries owned by the same runtime until restart.
- Behavior-delta runtime/preflight compilation is default-off through `NEST_AGENT_ENABLE_BEHAVIOR_DELTAS=0`. When enabled, it only compiles active relevant deltas, logs activations, and remains advisory. Proposed/staged low-risk deltas can auto-activate only when `NEST_AGENT_ENABLE_AUTO_ACTIVATE_LOW_RISK_DELTAS=1` and explicit validation metadata plus `MutationGate` evidence thresholds pass; policy/high-risk gates are unchanged, and broad automatic blocking is not performed beyond existing deterministic retry blocking.
- Non-secret runtime settings persist through a revision-checked transaction shared by the workbench and Telegram admin path. Candidate paths are validated before persistence; stale writers fail with HTTP 409; activation failure restores both the previous owner-only file and live config; API authentication remains launch-controlled. The Settings UI exposes `max_tool_rounds` as “Max tool calls” for new runs.
- New background runs persist a root task plus a small starter DAG with dependencies, required tools, risk, acceptance criteria, attempt count, failure reason, diagnosis, retry-strategy fields, and graph-runtime plan metadata.
- Ordinary conversation and observations must not write policy memory directly or self-assert promotion/approval provenance.
- The Memvid backend must use `.mv2` files and preserve one file per memory layer, including `.nest/memory/self.mv2`.
- `complete.mv2` is a run artifact under `.nest/runs/{run_id}/`, not a permanent memory layer.
- SQLite is control-plane state only. It is not the retrieval memory substrate.
- Support bundle exports are diagnostic artifacts only: they report environment-variable presence, redact common secret patterns, summarize state tables, and do not include raw broker vault contents or `.mv2` memory files.
- Mock-provider tests are the default fast validation path; Memvid integration remains behind `RUN_MEMVID_INTEGRATION=1`.
- Provider fallback only runs for `ProviderError(retryable=True)` failures; non-retryable errors fail fast and preserve the original provider error.
- MCP static tools remain approval-by-default unless a server is explicitly configured to trust reviewed manifest metadata; dangerous tool names/descriptions such as file writes, deletes, shell execution, patching, committing, or secrets are promoted to high risk during vetting. Dynamically discovered live tools always remain at least medium risk and approval-required.
- Invalid skill manifests are rejected during discovery; accepted skill manifests record validation status plus manifest/SKILL.md content hashes for provenance.
- Memory promotion decisions must carry auditable gate metadata, validation evidence refs, provenance, confidence, and validation status; one-off procedural successes and ordinary events can explain why they were not promoted into procedural/policy memory.
- Plugin review metadata, dependency locks, compatibility, signature/source provenance, and authority deltas can block install, update, or enablement; review is not host package installation. Executable plugin skills still need an explicitly declared, digest-pinned OCI runtime and canonical scopes before the separate containment runner can launch them.
